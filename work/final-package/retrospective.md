# Week 8 retrospective — draft for personal review

**This is an AI-assisted first-person draft based on the work in this repository. Edit it so it reflects what you actually remember and how you would naturally say it before submitting.**

In Week 1, I wanted to learn whether machine learning could help make content-review work more systematic. My initial idea was to build a score that tells an editor which pages to refresh. As I worked through the internship, I became more careful about the word “tells.” A model can sort a review queue, but the data I used does not show that changing a page will restore its traffic. The project changed from “find pages to refresh” into “help a person decide what to inspect first, then measure the result later.”

The work started with a research question about refresh opportunity scoring and a 30,000-row anonymized starter dataset. I wrote a data contract, checked signals, built a transparent prior-impressions baseline, and then compared logistic regression with that baseline. The final model used three inputs available before the cutoff: prior-window impressions, prior-window clicks, and age at cutoff. I held out entire clients rather than randomly splitting page rows, so pages from one client could not appear in both train and test. The model ranked 49 of the first 50 held-out rows as declining, compared with 46 for the prior-impressions rule. The test set had a 91.1% decline rate, though, so the apparent precision is easier to achieve than it would be in a balanced population. The measured gain is three rows on one split, not evidence of a broad or lasting improvement.

One thing that changed in how I work is that I now ask where each input comes from in time before trusting a model. A field that is recorded after the cutoff, or derived from the answer, can make a result look much better than it is. I also learned that validation design changes the question: holding out clients checks whether a pattern transfers to unseen clients in the same snapshot, while a future-time holdout would be needed to test what happens later. The grouped split is stronger than a random row split for this dataset, but it still does not substitute for future validation.

A second transferable lesson is to compare against a simple baseline on the same rows and metrics. The model did beat the prior-impressions rule across the reported ranking metrics, but the high base rate and small top-50 difference keep that finding in perspective. It is useful to show the baseline beside the model because a single large-looking metric can hide how much of the result comes from the labels being common.

A third lesson is that a model output should connect to a real, bounded action and a human check. An editor could use the ranking to decide what to review first, then confirm current accuracy, source freshness, intent, and measurement quality. The model cannot make those checks and should not publish, delete, or rewrite pages automatically. Clear limitations make the output more useful because they show where a person must take over.

Next, I would run a time-forward evaluation when an approved later window is available, record how often editors accept or reject the ranked suggestions, and compare the model with the baseline across multiple client splits. I would also add the FL-07 Study Notes Assistant as a portfolio case study, keeping its local-only design and its limitations visible. The three habits I want to carry into future work are: trace every feature to a valid point in time, keep a simple baseline beside the model, and define the human decision the result is meant to support before trying to optimize the score.
